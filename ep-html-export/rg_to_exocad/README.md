# RealGUIDE → exocad webview (PoC)

Конвертер данных кейса, экспортированного из **RealGUIDE**, в бинарный
формат `DentalWebGL.m_Data`, который понимает **родной exocad webview**
(тот HTML-экспорт, что генерирует сам exocad — движок three.js + асимметричный
крипто-модуль + свой парсер сцены). Идея: подменить внутри оригинального
exocad-файла встроенные данные кейса на данные из RealGUIDE — и получить
файл, который exocad webview открывает как свой родной.

**Статус: рабочий proof-of-concept**, проверено вживую (headless Chromium +
скриншот): все меши грузятся, дерево объектов и цвета — корректные, камера
после фикса верно наводится на всю модель.

## Как это сделано

Формат `DentalWebGL.m_Data.data` (сырой бинарник в base64, без gzip) был
разобран не по догадке, а трассировкой **настоящего кода** exocad-парсера,
найденного внутри их же движка (класс `BinaryFileParser` и цепочка
`parseScene → createScene → parseCTMData → MeshImportCTM.parseMeshFromBinary`).
Из этого разбора получилась точная побайтовая спецификация:

- Примитивы: `int32`/`float32`/`bool`(=int32) LE; строка — `int32`-длина +
  UTF-8-байты, поле выровнено до кратности 4 (`4*ceil(len/4)`); цвет — 3
  байта RGB + 1 байт паддинга; матрица 4×4 — 16 float, **column-major**
  (порядок THREE.Matrix4.elements, т.е. это ТРАНСПОНИРОВАННАЯ обычная
  row-major матрица).
- Заголовок: версия, язык, (если версия>5) 2 GUID кейса, пустая строка
  (иначе — ветка с паролем/AES), билд движка (2 строки), источник света,
  фоновая картинка (можно 0), "свои" виды камеры (0), "виды по умолчанию"
  (нужен минимум 1 — из его матрицы движок берёт стартовую позицию/поворот
  камеры), число аннотаций (0 в PoC).
- Каждый меш: 3 bool-флага, 5 цветов (ambient — не используется, но байты
  обязаны быть; diffuse/specular/emissive/select), 3 float (прозрачность-
  заглушка, shininess, неиспользуемый), ещё один float (polygon offset),
  матрица трансформации, сама геометрия (см. ниже), текстура (можно 0),
  ещё один float — реальная прозрачность, путь в дереве объектов
  (`[{Имя группы, цвет}, {Имя объекта, цвет}]` — то самое дерево "Показать/
  скрыть" в интерфейсе), и (по версии) флаги видимости/wireframe/point-cloud.
- Геометрия — открытый формат **OpenCTM**, метод **RAW** (без сжатия;
  движок сам умеет его читать — там встроен `ctm-js`). Формат подтверждён
  по их же исходнику (`CTM.CompressionMethod.RAW=5718354` — это ASCII
  `"RAW\0"` как int32) и проверен обратной загрузкой через нативную
  библиотеку `openctm` (pip) на реальных данных.

Подробности и находки по ходу разбора (номера смещений, хекс-дампы) не
сохранены как отдельный документ — вся логика перенесена в код
(`binfmt.py`, `ctm_raw.py`, `mesh_record.py`).

## Файлы

- `ctm_raw.py` — запись геометрии в OpenCTM RAW.
- `binfmt.py` — `BinaryWriter`: примитивы бинарного формата (зеркало
  `BinaryFileParser` из движка exocad, но на запись).
- `mesh_record.py` — запись одной записи меша по разобранной схеме.
- `rg_load.py` — чтение сцены из RealGUIDE-экспорта (`D3DS`-контейнер:
  JSON-заголовок + geoms с квантованной геометрией), деквантизация,
  вычисление сглаженных нормалей.
- `build_exocad.py` — сборка: RealGUIDE `scene.bin` → бинарь `m_Data` →
  подстановка в оригинальный exocad-шаблон.

## Важный костыль: направление камеры

Внутри матрицы вида (`Views`) колонка 2 (`elements[8..10]`) в РАЗНЫХ
местах движка трактуется по-разному:
- при первой, "сырой" настройке камеры в `createScene()` она передаётся в
  `camera.lookAt(...)` — а туда можно передать хоть абсолютную точку, хоть
  направление, результат почти не отличается на большом расстоянии;
- но во ВСЕХ функциях наведения камеры (`createView`, `zoomToSphere`,
  `setViewMatrix`, дергаются при переключении видов/автофреймовке) она же
  читается как **единичный вектор направления** и напрямую умножается на
  вычисленную дистанцию.

Если туда записать абсолютную точку (например, центр сцены, а не
единичный вектор направления к нему), при первой же автофреймовке позиция
камеры улетает на порядки — это ушло много времени на отладку. Тут это
пофикшено (`build_m_data` пишет туда нормализованное направление), заодно
после загрузки сцены впрыскивается небольшой скрипт, который вызывает
`CameraManager.setViewMatrix(matrix, CUBE)` — это единственный найденный
вызов, который синхронизирует и камеру, и её trackball-controls (простое
присваивание `camera.position` не держится — на следующем кадре его
перетирает `TrackballControls.update()`).

## Использование

```
python3 build_exocad.py <realguide_scene.bin> <exocad_webview_shell.html> <output.html>
```

- `<realguide_scene.bin>` — распакованный (gunzip) `#d3d-scene-payload` из
  HTML-экспорта RealGUIDE (см. `../README.md` про формат `D3DS`).
- `<exocad_webview_shell.html>` — **ваш собственный** файл, полученный
  экспортом "webview" прямо из exocad/ExoPlan. Он **сознательно не хранится
  в этом репозитории** — это проприетарный бандл exocad GmbH (copyright
  в шапке файла), не наш код; скрипт только временно встраивает в НЕГО
  наши данные.
- `<output.html>` — итоговый файл для проверки в браузере.

## Ограничения PoC

- Геометрия пишется без сжатия (OpenCTM RAW) — итоговый файл заметно
  больше, чем родной exocad-экспорт (который использует сжатый MG2).
  Для продакшена стоит добавить MG2-энкодер или хотя бы zlib/deflate
  поверх RAW-блоков.
- Аннотации/измерения из RealGUIDE-кейса не переносятся (пишем 0).
- Проверено только на одном реальном RealGUIDE-кейсе и headless Chromium;
  живого экспорта из ExoPlan для сверки схемы имплантов пока не было.
