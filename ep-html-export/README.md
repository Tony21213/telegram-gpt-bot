# EP HTML EXPORT

Самодостаточный HTML-вьювер для экспорта 3D-планов **ExoPlan** (модуль
имплантологического планирования exocad) — по тому же принципу, что и
вьювер, который уже сделан для RealGUIDE: один HTML-файл без зависимостей,
открывается двойным кликом в браузере, ничего не грузит из сети.

**Статус: в разработке.** Ниже — то, что уже готово, и то, что ещё предстоит
(в первую очередь — нужен реальный файл экспорта из ExoPlan, чтобы написать
парсер под его формат).

## Идея

Не писать 3D-вьювер с нуля, а переиспользовать движок, который уже
используется в HTML-экспорте для RealGUIDE (тёмная тема, панель слоёв,
карточка импланта, линейка/измерения, комментарии, режим коррекции позиции
и т.д.) — и написать только **конвертер**, который превращает данные проекта
ExoPlan в тот же формат "сцены", который этот движок понимает. Сам движок
(vendor/viewer_engine.js) не модифицируется.

## Структура проекта

```
ep-html-export/
  vendor/
    viewer_engine.js      — движок вьювера (JS), извлечён из рабочего
                             realguide-экспорта, НЕ модифицирован
    shell_template.html   — HTML-оболочка (разметка + CSS) того же экспорта,
                             с добавленным режимом "no-ct" (см. ниже) и
                             плейсхолдерами __TITLE__ / __SCENE_PAYLOAD__ /
                             __VOL_PAYLOAD__ / __VIEWER_GZ__
  lib/                     — конвертер (Python), ещё не написан
  examples/                — тестовый кейс для проверки пайплайна
```

## Как устроен формат сцены (то, что уже разобрано)

Разбор реального realguide-экспорта (`project12_2_edited.html`, 27 МБ)
показал следующую структуру. Она нужна нам, чтобы генерировать HTML,
совместимый с движком `viewer_engine.js` без его модификации.

Файл-экспорт — это `shell_template.html` с тремя `<script>`-пейлоадами,
каждый — gzip, потом base64:

- `#d3d-scene-payload` (`type="application/rg+gzip"`) — JSON сцены
  (список мешей, импланты и их параметры, комментарии, измерения).
- `#d3d-vol-payload` (`type="application/rg-vol+gzip"`) — объём КТ
  (кросс-секции, панорама). **Обязателен** — движок бросает исключение,
  если тега нет в DOM, даже если реальных вокселей нет.
- `#rg-viewer-gz` (`type="application/gzip"`) — сам движок, тоже gzip+base64
  (в vendor/viewer_engine.js хранится уже распакованным, в виде обычного
  читаемого JS — конвертер сам будет паковать его обратно при сборке
  финального HTML).

### Scene JSON (упрощённый — тот вариант, который используем мы)

Движок поддерживает два формата сцены: "упакованный" (с квантованной
геометрией, магическая сигнатура `D3DS`) и обычный, где меши хранят готовые
`Float32Array`/`Int32Array` в base64. Мы используем **второй, простой**
вариант — не нужно реализовывать квантование.

```jsonc
{
  "version": 3,
  "mode": "full",
  "title": "Название кейса",
  "exported_at": "2026-09-15T12:00:00.000Z",
  "volume": { "codec": "d3dvol-v1", "ref": "#d3d-vol-payload" },
  "comments": [], "measurements": [], "slice_markers": [],
  "viewer_defaults": { "mesh_color": "#c8c8c8", "theme": "dark", "window": 2800, "level": 600 },

  // Импланты — данные для карточки "Информация об имплантах" и для
  // автоматической привязки абатмент/гильза → нужный имплант (по
  // расстоянию transform-позиции меша до sites[].origin, см. ниже).
  "sites": [
    {
      "id": "site-16", "kind": "implant", "tooth": "16",
      "origin": [x, y, z],   // точка платформы импланта, мм
      "axis":   [x, y, z],   // направление оси импланта (единичный вектор)
      "mesial": [x, y, z],   // ориентир "мезиально" (единичный вектор)
      "r": 2.0, "length": 10.0, "visible": true, "color": [255, 200, 0],
      "info": {
        "manufacturer": "...", "model": "...", "article": "...",
        "diameter": 4.0, "length": 10.0,
        "abutment": { "manufacturer": "...", "model": "...", "size": "...", "article": "..." },
        "sleeve":   { "manufacturer": "...", "model": "...", "article": "...", "distance": 7.0 }
      }
    }
  ],

  // Меши — каждый объект 3D-сцены (скан, зуб, имплант, абатмент, гильза,
  // шаблон, антагонист, мягкие ткани...).
  "meshes": [
    {
      "id": "m0", "name": "16", "kind": "implant",
      "visible": true, "opacity": 1, "flat_shading": false,
      "mesh_color": "#fd33df",
      "transform": [ /* 4x4, row-major: [R|t; 0 0 0 1], 16 чисел */ ],
      "buffers": {
        "positions_b64": "<base64 Float32Array, локальные координаты>",
        "indices_b64":   "<base64 Int32Array, тройки индексов треугольников>"
      }
    }
  ]
}
```

Важные правила, по которым движок сам связывает меши с `sites[]`
(проверено чтением `viewer_engine.js`, функции `meshBelongsToSite` /
`nearestSiteForMesh` / `jawOfMesh`):

- Меш с `kind: "implant"` или `"pin"` привязывается к сайту **по имени**:
  `mesh.name` должно совпадать с `site.tooth` (например, оба — `"16"`).
- Меш с `kind` в `abutment` / `analog` / `sleeve` привязывается **по
  расстоянию**: движок берёт `[transform[3], transform[7], transform[11]]`
  (это перенос в матрице трансформации меша) и ищет ближайший `site.origin`
  (в пределах 14 мм). Поэтому для таких мешей достаточно выставить перенос
  трансформации равным `site.origin` соответствующего импланта — вращение
  можно оставить единичным, конвертеру не нужно восстанавливать локальную
  систему координат импланта.
- Челюсть (верхняя/нижняя) определяется **по имени меша**: если имя
  содержит "нижн"/"lower"/"mandib" — нижняя, иначе верхняя (кроме
  `kind: "antagonist"`, тот всегда считается нижней).
- `cpr_arch` (дуга для панорамной реконструкции) можно не указывать —
  при отсутствии движок сам строит дугу по позициям `sites[]` или по
  форме сканов челюсти.

### Vol payload — как обойтись без реального КТ

ExoPlan обычно не поставляет объём КТ (в отличие от RealGUIDE) — это
дизайн-система, а не программа сведения снимков. Поскольку `#d3d-vol-payload`
обязателен для движка, конвертер всегда кладёт **минимальный пустой объём**
(формат `D3DV`, версия 2): все воксели помечены как "не занято" — тогда
residual-поток пустой и распаковка тривиальна.

```
"D3DV" (4 байта) | version=2 (uint32 LE) | headerLen (uint32 LE) | header JSON
  header = {"dims":[2,2,2], "spacing":[1,1,1], "origin":[0,0,0],
            "direction":[1,0,0,0,1,0,0,0,1], "hu_air":-1000, "occupied":0}
далее: битовая маска occupancy — ceil(n/8) байт, все нули (residual-поток пустой)
```

Чтобы такой "пустой" КТ не путал пользователя вьювера, `shell_template.html`
получил доп. CSS/класс `#app.no-ct` (наша добавка поверх движка, сам движок
не трогали): прячет колонку срезов КТ и кнопку панорамы, разворачивает
3D-вид на всю рабочую область. Конвертер выставляет этот класс, когда
реального КТ нет.

## Разведка нативного формата exocad (для будущего)

Мне прислали реальный webview-экспорт **DentalCAD** (не ExoPlan) —
`exocad_data.bin` после base64-декодирования содержимого
`DentalWebGL.m_Data.data`. Он оказался **не зашифрован** и разбирается
напрямую:

- Строки — `uint32 LE` (длина в байтах) + UTF-8 без завершающего нуля
  (кроме первой, языковой строки — там встретился доп. паддинг).
  Так нашлись понятные ярлыки объектов: `"Сканы челюстей"`,
  `"Антагонисты"`, `"Объединённые части"`, `"Объединенная балка (12-...-22)"`,
  `"Винтовые каналы"`, `"22: Винтовой канал"` и т.д. — то есть реальная
  таксономия групп объектов exocad.
- Геометрия мешей хранится в открытом формате **OpenCTM** (сигнатура
  `OCTM`, метод сжатия `MG2` — квантованные вершины/нормали + сжатие).
  Формат открытый и документированный (openctm.sourceforge.net). На PyPI
  есть пакеты `openctm`/`pyctm` — быстрая проверка нашла их в индексе, но
  установка/импорт в этом окружении не была доведена до конца и не
  проверялась в деле; это не готовый путь, а зацепка для будущей работы.
- Встречаются встроенные PNG (иконки видов, превью).

Этого достаточно, чтобы при необходимости написать нативный парсер
webview-экспорта exocad — но: (а) это был файл DentalCAD, а не ExoPlan,
структура имплантологических полей (позиции/оси имплантов, абатменты,
гильзы) в нём не проверялась; (б) декодер MG2 (сжатие OpenCTM) ещё не
реализован и не протестирован. Это задел на будущее, а не рабочий путь
прямо сейчас.

## Текущий план конвертера (то, что делаем в первую очередь)

Пока нет образца реального экспорта ExoPlan, конвертер строится на
собственном промежуточном формате **`manifest.json` + STL-файлы**
(ExoPlan умеет экспортировать каждый объект кейса отдельным STL — это
стандартная, всегда доступная функция, в отличие от закрытого webview-
формата). Как только появится реальный файл экспорта ExoPlan — добавим
нативный парсер, который будет производить тот же `manifest.json` (или
сразу тот же scene JSON), не трогая остальной пайплайн (`lib/scene_pack.py`,
`lib/html_pack.py`).
